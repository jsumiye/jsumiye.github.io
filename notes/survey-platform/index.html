A survey stack for K-12, from builder to PDF

May 2025

A client needed a replacement for a survey platform that was being retired. The new system had to import the old survey files, support a survey builder, store roster credentials, and generate letter-size PDF reports. Those files contained school names, question order, and historical response data that had to remain usable.

The sections below describe how a survey moves through the system.

flowchart TB qst["QST / DAT / CSV"] --> db builder["SurveyJS builder"] --> db db[("MySQL surveys, responses, roster toolbox, templates, PDFs")] db --> slug["Slug + vanity public taker roster fill open / expire"] db --> reports["Reports single / compare"] reports --> pdf["/report/slug shareable PDF"]

The builder writes a survey. The public taker writes responses. Reporting reads both and draws charts that can be compared across years. A roster CSV supplies per-student passwords when a survey is not meant to be an open form.

Survey management

Staff work from one table. Each row includes category, author, archive status, school, state, season, year, response count, and optional open and expire times. Those timestamps are stored in UTC and converted in the browser so a survey can open at a local midnight in another time zone.

Visibility is private, unlisted, or public. Private surveys stay in the admin table. Unlisted surveys are reachable only by link. Public surveys appear on the homepage after a state is selected, and only while the schedule window is open. Each survey has a short slug and an optional vanity path. Staff can copy the link, and the URL stays visible if the clipboard is unavailable.

Duplicate copies a survey so a new season does not start from a blank form. The table sorts, pages, and filters so staff can find a prior-year survey by school.

Legacy import

The importer reads a legacy survey file and, optionally, a file of responses. The filename is parsed for state, campus, and school year. That campus guess is matched against existing school names after common suffixes like "academy" and "high school" are stripped. A wrong school name creates a duplicate campus. A wrong question order breaks year-over-year charts.

The parser runs as a sequence of checks rather than a single conversion step. Question types from the old system map onto the builder. Checkboxes expand to one column per choice. Matrix questions flatten to one column per row. Some response files start with a date field, so the mapper skips those leading cells instead of shifting answers. Choice ids are preserved so an imported survey can still be edited. The toolbox is limited to the question types the reports know how to chart.

Custom toolbox questions are stored in the database and loaded into the builder. Reusing the same internal question name keeps reports aligned across schools even when the visible title differs.

Student access and response data

A survey may require a password. When it does, staff upload a roster of names, passwords, and optional student details. An upload replaces the existing roster for that survey. It runs in a transaction, checks the headers, and rejects a row with an invalid email. The taker looks up the password and fills the matching hidden fields. Empty cells are left empty.

Emails sometimes arrive after responses have been submitted. A backfill updates the roster and writes the address onto stored responses that already contain that password.

Exports keep question order, including checkbox choice order, so a file can be downloaded and uploaded again without column drift. Names with apostrophes and accented characters are written as UTF-8.

Nightly database dumps are stored on the host. Restore selects a single survey from a backup instead of importing the full dump.

Reporting and PDF export

Reports are built on a grid. Charts and tables can be dragged, resized, centered, or deleted. Filtered summary tables can slice by question, answer choice, or a demographic field. A layout can be duplicated and renamed for a later year.

Comparison reports align questions across surveys. The matcher ignores leading numbers and punctuation, then compares titles, so a numbered question can match the same wording without the number. Manual mapping is available when a question was rewritten on purpose.

Page templates store empty chart frames. Advanced templates also store which question name feeds each chart. Comparison templates store the side-by-side layout.

The export is a letter-size PDF with a repeating header and footer. Saving it issues a shareable link, shows the file in the browser, and counts views. Report links are kept out of search indexes.

Notable security features

  • Admin changes require a CSRF token checked against the session.
  • Passwords are stored as hashes. A failed login returns a generic error so valid emails cannot be enumerated.
  • Session cookies are HttpOnly, Secure on HTTPS, and SameSite Lax.
  • Database access uses prepared statements. Roster names, emails, and student numbers are never concatenated into queries.
  • Responses send standard browser hardening headers, and cross-origin access is limited to known site origins.
  • Oversized uploads are rejected. PDF uploads are checked for file type before they are written to disk.
  • Backup restore refuses a path that leaves the backup directory.
  • Roster uploads check required headers and email format inside a transaction. Invalid rows abort the replace.
  • Shared PDF links are kept out of search indexes. Surveys can be private, unlisted, or public, with optional per-student passwords.
